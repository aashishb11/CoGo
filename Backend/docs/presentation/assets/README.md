# Presentation diagram assets

Static, slide-ready diagrams broken into modules so the conceptual and DB schemas can be explained one region at a time instead of dumped whole on a slide.

Each module has a `.mmd` source in `src/` and renders to both PNG (raster, 16:9, scale 2) and SVG (vector) in `out/`. Drop the file straight into PowerPoint / Keynote / Google Slides.

## How to use in a deck

Suggested slide order (one module per slide):

| #   | File                                | What to say                                                                                                                                                                                                                                                                                                                                                                             |
| --- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `00-overview`                       | Seven domains, dependency flows left-to-right. Rides & Bookings is the central node — every other module attaches there.                                                                                                                                                                                                                                                                |
| 2   | `01-identity-conceptual`            | User + Profile is 1:1. Org is optional. Badges are inline JSONB (no separate table) — small, per-user, never queried cross-user.                                                                                                                                                                                                                                                        |
| 2   | `01-identity-db`                    | Same shape at the DB level. `profiles.user_id` is PK _and_ FK — that enforces the 1:1 without a surrogate id.                                                                                                                                                                                                                                                                           |
| 3   | `02-auth-db`                        | Platform plumbing — better-auth + per-device push. Not in the conceptual diagram because it isn't a business concept. `verification` floats because it's identifier-keyed (email), not user-keyed.                                                                                                                                                                                      |
| 4a  | `03a-trips-conceptual-hierarchy`    | Trip is abstract — SporadicTrip (one departure) and RecurringTrip (calendar pattern). At the DB level this is single-table inheritance (`type` discriminator).                                                                                                                                                                                                                          |
| 4b  | `03b-trips-conceptual-relations`    | Each Trip uses one Car, which is_a one CarModel. The CO₂ math reads `co2KgPerKm` off the model. Two Location associations (origin / destination) — drawn as two boxes for clarity.                                                                                                                                                                                                      |
| 4   | `03-trips-db`                       | One `trips` table for both subtypes. `departure_at` non-null for sporadic; `schedule jsonb` carries the recurring pattern.                                                                                                                                                                                                                                                              |
| 5   | `04-rides-conceptual`               | **The heart**. Trip is the contract template; Ride is its frozen, dated instance. Booking is a passenger asking for a seat on a Ride. Snapshot semantics — once a Ride completes or cancels, its origin / destination / distance / CO₂ are immutable.                                                                                                                                   |
| 5   | `04-rides-db`                       | Same shape — note `rides` carries all the snapshotted columns. `bookings.boarded_at IS NOT NULL` is the authoritative "did they board?" signal.                                                                                                                                                                                                                                         |
| 6   | `05-chat-conceptual`                | One thread per (Trip, passenger) — recurring trips keep one continuous driver↔passenger conversation across all generated rides. Two participants, derived from the trip; no participant join table.                                                                                                                                                                                    |
| 6   | `05-chat-db`                        | Per-role read cursors (`driver_last_read_at`, `passenger_last_read_at`) drive unread counts on the inbox. Soft-delete only — bodies are hidden, rows stay for ordering and audit. Footnote (skip in the slot, mention if asked): `chat_messages.ride_id` exists as a nullable FK so the sender can tag a message with a specific ride for the FE to render; no read path queries by it. |
| 7   | `06-wallet-conceptual`              | Wallet is the single ledger. Holds reserve funds at booking accept; resolve to _captured_ (boarding) or _released_ (cancellation).                                                                                                                                                                                                                                                      |

## Regenerating

If you edit any `.mmd` file, re-run:

```bash
./build.sh
```

This calls `pnpm dlx @mermaid-js/mermaid-cli@10.9.1` for each source, using your local Chrome (via `puppeteer.config.json`) so puppeteer doesn't download a second Chromium. Output canvas is 1920×1080 (16:9); PNG is rendered at scale 2 for crisp slide insertion.

## Layout choices worth knowing

- Almost every diagram uses `direction LR` and the `elk` layout engine — that combination produces wider-than-tall images with very few crossings.
- Trips is split into two diagrams (hierarchy + relations) because trying to show both in one frame fought ELK's layout — inheritance wants to stack vertically, associations want to flow horizontally.
- The Auth module exists in the DB rendering only. Conceptual modeling doesn't include platform-level tables like sessions or push subscriptions, so the slide should explain _why_ they exist (web platform reality, not business need).
- Boundary entities (e.g. `Trip` appearing in the Rides slide) are drawn as bare boxes with no attributes — they're context, not the focus of that slide.
- The two `09-full-*` diagrams are intentionally busy. They're the "this is everything we just walked through" reveal — point at clusters, don't try to read them.
