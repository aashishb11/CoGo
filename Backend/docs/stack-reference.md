## Database & ORM

**PostgreSQL 17** via **Drizzle ORM**.

| Package | Version | Purpose |
|---------|---------|---------|
| `drizzle-orm` | 0.45.2 | Type-safe ORM |
| `drizzle-kit` | 0.31.10 | Migration generator + Drizzle Studio |
| `postgres` | 3.4.8 | postgres-js query client |

**How Drizzle is used here:**
- Schema lives in `core/database/schema/` as separate `.schema.ts` files, one per domain.
- `schema/index.ts` re-exports all tables.
- Rows are typed via `$inferSelect<T>` / `$inferInsert<T>` — no hand-rolled interfaces.
- Transactions: `db.transaction(async (tx) => { ... })`, `tx` passed as first arg through repositories.
- Migrations are auto-generated by `drizzle-kit generate` and applied at startup via `drizzle-kit migrate`.

**Local development:** Docker Compose runs Postgres 17.  
**Production:** Neon PostgreSQL (serverless Postgres, connect via `DATABASE_URL`).

## Real-Time — WebSocket Chat

**Socket.IO** via NestJS gateway.

- Namespace: `/chat`
- Auth: Bearer token or cookie session verified on connect.
- Events: `joinThread`, `sendMessage`, `markThreadRead`, `deleteMessage`.
- Chat threads are 1:1 per (trip, passenger).
- Messages persisted to DB and broadcast in real-time.

**Key pattern:** WebSocket gateway and REST API are co-located in the same NestJS process — no separate socket server.

## Push Notifications

Dual-transport: web browsers (Web Push) and React Native (Expo).

| Package | Version | Purpose |
|---------|---------|---------|
| `web-push` | 3.6.7 | VAPID + Web Push Protocol |
| `@better-auth/expo` | 1.6.9 | Expo push token handling |

**How it works:**
1. Client registers a subscription via `POST /api/notifications/subscriptions`.
2. Server detects endpoint type via `isExpoPushToken()` — Expo tokens look like `ExponentPushToken[...]`.
3. Web Push uses VAPID keys; Expo uses Expo access token.
4. Per-device settings stored in `push_subscriptions.settings` JSONB (e.g., `traffic_alerts` toggle).
5. Notifications sent async, never blocking the request.

**Triggered by:** Cron jobs (traffic alerts), domain events (ride completed), direct actions (driver no-show).

| Package | Version | Purpose |
|---------|---------|---------|
| `stripe` | 21.0.1 | Stripe Node.js SDK |

**Features implemented:**
- **Top-ups:** Stripe Checkout sessions (one-time payments).
- **Driver Payout Onboarding:** Stripe Connect Express accounts.
- **Withdrawals:** Stripe transfers to connected accounts.
- **Webhooks:** `checkout.session.completed`, `account.updated` — verified with Stripe signature.

**Wallet pattern:**
- Append-only `wallet_transactions` ledger (topup / payment / earning / withdrawal).
- `wallet_holds` tracks active booking reservations (placed on accept, released on cancel, captured on boarding).
- `WalletService` is the sole writer of balances — no other service touches the wallet directly.

## Architecture Pattern

**Layered, modular, domain-driven.** Four top-level source directories:

```
src/
  core/         Framework infrastructure (DB, config)
  integrations/ External service adapters (Stripe, Mail, Maps, etc.)
  modules/      Domain feature modules (auth, trips, wallet, etc.)
  shared/       Cross-module primitives (errors, events, geo, i18n)
```

### Inside every feature module

```
module-name/
  module-name.controller.ts   HTTP routing only — no business logic
  module-name.service.ts      Use-case logic, transaction management
  module-name.repository.ts   Single-table data access, no business rules
  module-name.mapper.ts       DB row → response DTO (outbound only)
  module-name.types.ts        Status enums, value objects for this module
  dto/                        Request + response DTOs (class-validator)
  domain/                     Pure functions — no I/O
```

### Request flow

```
HTTP Request
  → Controller (validates DTO, extracts session)
    → Service (business rules, transactions)
      → Repository (SQL via Drizzle, returns null not exceptions)
        → DB (Postgres)
      ← Repository
    ← Service (null → throws NestJS exception)
      → Mapper (DB row → response DTO)
  ← Controller → HTTP Response
```

### Key rules enforced

- Repositories return `null` for not-found — Services convert to exceptions.
- Transactions flow as `tx: DbClient` as the first argument.
- Cross-module imports use path aliases (`@modules/trips`); intra-module imports are relative.
- Domain layer (pure functions) never imports ORM or NestJS — testable in isolation.
- `WalletService` is the sole writer of wallet state — enforced by convention.

## Domain Events

NestJS `EventEmitter` used for intra-process domain events.

- Event names in `shared/events/event-names.ts` (e.g., `DOMAIN_EVENTS.RIDE_COMPLETED`).
- Payloads typed in `shared/events/payloads.ts`.
- Subscribers (`*.subscriber.service.ts`) decoupled from the publishing service.
- Failures in subscribers are logged, not propagated — they never roll back the triggering request.

## Cron Jobs

Three periodic sweeps run inside the API process (no separate worker):

| Service | Schedule | Does |
|---------|----------|------|
| `BookingsExpiryService` | `*/15 * * * *` | PENDING bookings on past rides → EXPIRED |
| `TrafficWatcherService` | Every 10 min | Fetch traffic for upcoming rides, push alerts on delay change |
| `RidesSweepService` | `1 * * * *` | Idle in-progress → COMPLETED; stranded active → CANCELLED (driver_no_show) |

## Error Handling

Consistent error shape across all endpoints.

```json
{
  "code": "ERROR_CODE_STRING",
  "statusCode": 400,
  "message": "Human-readable message",
  "details": {}
}
```

- **Central registry:** `ERROR_CODES` enum in `shared/errors/error-codes.ts`.
- **Global filter:** `GlobalExceptionFilter` normalizes all NestJS exceptions.
- **Typed throw helpers:** `throwBadRequest()`, `throwConflict()`, `throwNotFound()`, etc.
- **Rich codes:** Some codes carry structured `details` (e.g., `INSUFFICIENT_WALLET_BALANCE` with balance and required amount).

## Database Schema — Table Overview

| Table | Notes |
|-------|-------|
| `users` | Core identity (Better Auth managed) |
| `profiles` | 1:1 extension of users (bio, CO2, XP, badges JSONB) |
| `sessions` / `accounts` / `verification` | Better Auth tables |
| `organizations` | Multi-org with email domain verification |
| `cars` | Driver fleet (soft-delete for ride history) |
| `car_models` | CO2 emission data (soft-delete) |
| `trips` | Templates — single-table inheritance: `sporadic` vs `recurring` |
| `rides` | Frozen instances generated from trips |
| `bookings` | Seat reservations with status lifecycle |
| `chat_threads` | 1:1 per (trip, passenger) |
| `chat_messages` | Soft-delete safe |
| `push_subscriptions` | Per-device, per-user (endpoint unique index) |
| `wallets` | 1:1 user balance ledger |
| `wallet_transactions` | Append-only (topup / payment / earning / withdrawal) |
| `wallet_holds` | Active booking money reservations |
| `trusted_contacts` | 1:1 per user (safety gate) |
| `safety_incidents` | Append-only incident reports |
| `user_ratings` | Append-only, unique `(ride_id, rater_id, ratee_id)` |
| `user_favorite_trips` | Trip bookmarks |

**Notable schema patterns:**
- Partial-unique indexes (e.g., `wallet_holds WHERE status = 'active'`) prevent concurrent double-holds.
- JSONB columns for variable-length arrays (`badges`, `schedule`, `push_subscriptions.settings`).
- All enum values stored as text constants (not Postgres enums) for migration safety.

## What to Reuse for a New Mobile App Backend

If you're bootstrapping a new NestJS backend for a React Native / Expo app, here's the priority list from this repo:

1. **Same stack:** NestJS + Drizzle ORM + PostgreSQL (Neon) + pnpm + TypeScript strict.
2. **Auth:** Better Auth with `@thallesp/nestjs-better-auth` + `@better-auth/expo`. Handles Expo cookie/session quirks out of the box.
3. **Push:** `web-push` (VAPID) for web, Expo push for native. The dual-transport routing pattern in `NotificationsService` is clean and reusable.
4. **Payments:** Stripe + Stripe Connect if you need driver/seller payouts.
5. **Real-time:** Socket.IO gateway co-located with REST API — no separate process needed at this scale.
6. **Architecture:** Controller → Service → Repository + Mapper + Domain (pure). Works extremely well. Don't skip the Mapper layer.
7. **Error handling:** Global exception filter + central `ERROR_CODES` enum + typed throw helpers. Saves a lot of inconsistency.
8. **Validation:** `class-validator` + `class-transformer` + `ValidationPipe` globally.
9. **Logging:** `nestjs-pino` — zero config, structured output.
10. **Email:** Brevo SMTP API (generous free tier, good deliverability).
11. **Maps/Routing:** Google Maps API for anything route-related.
